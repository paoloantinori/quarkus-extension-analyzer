# Ablation bench: empirical ground truth for recurring suspects (TASK-21)

**Date:** 2026-08-15. **Method:** for each recurring suspect, remove ONLY that
`<dependency>` from the app pom, run `mvn package -DskipTests`, record the
outcome, restore the pom (backup-first; every pom verified restored). Where the
build passed, the produced artifact was inspected structurally (jar contents,
generated classes) to determine runtime impact, because Quarkus augmentation
makes `mvn package` alone an unreliable oracle: extensions contribute
build-step-generated implementations (native method bodies, serializers) whose
absence only manifests at runtime.

## The numbers

- 14 recurring suspects ablated: **9 false positives, 5 true suspects** (suspect-verdict precision
  ≈ 36% on this recurrence-heavy sample; the broader 21-app matrix had 8/14 apps at zero
  suspects, so overall precision is far higher; this bench deliberately concentrates on the
  hard residual).
- Of the 9 false positives, the **extension form already resolves 6** (config-yaml via the
  file rule; rest-qute via the Qute rule; quarkus-rest via the jakarta.ws.rs rule).
- **Unresolved false positives: 2 families.**
  1. `quarkus-rest-jackson` (serialization-only): build passes, serializer absent at runtime.
     Signal idea: REST used (resources present) + a declared REST-serializer extension as
     suspect + endpoints returning non-String POJOs → credit. Needs endpoint return-type
     analysis in the bean index.
  2. `quarkus-reactive-pg-client` (reactive driver selection): selected by the reactive
     datasource stack, not by bytecode or config key alone. Signal idea: hibernate-reactive
     declared+used AND a reactive-* client suspect → credit.

## Methodological finding (as important as the numbers)

`mvn package` success after removing an extension is NOT evidence the extension was
removable, in Quarkus. Two mechanisms produce silent runtime breakage:

1. **Native-method templates** (`@CheckedTemplate`): the synthetic `Templates` class has
   `native` methods whose bodies are generated by the extension's build step. Without the
   extension the build still passes; the method has no implementation
   (UnsatisfiedLinkError at first call).
2. **Provided serializers** (`quarkus-rest-jackson`): REST endpoints returning POJOs need a
   serializer extension; without it the classes still compile (Jackson API arrives
   transitively elsewhere or is unused in code), the build passes, and the fast-jar simply
   contains no serializer.

Any dependency-removal workflow on Quarkus (including a human following the tool's
report) must verify at runtime, not just rebuild. The tool's suspect note should say so.
